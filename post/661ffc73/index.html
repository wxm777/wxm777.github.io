未授权访问复盘：API网关多实例鉴权不一致致5万条学生信息泄露

发表于 2026-08-22 分类于 实战复盘 本文字数： 4.9k 阅读时长 ≈ 4 分钟

0x00 前言

未授权访问类漏洞的测试逻辑通常很简单：不带会话凭据请求接口，返回数据就是漏，返回 401/403 就是没漏，大部分自动化扫描器也是按这个逻辑判定的。

但本次对某高校数字校园的测试中，我遇到了一个不符合上述规律的现象：同一个接口、同样不带任何凭据，前一次请求返回”无权限”，后一次请求直接返回完整的业务数据，且两种响应严格交替出现。如果按常规流程只请求一次就下结论，这个漏洞有约 50% 的概率被判定为不存在。

本文复盘这个漏洞的完整挖掘过程：从前端 JS 提取 API 攻击面，识别负载均衡导致的鉴权不一致，用对照实验圈定缺陷范围，在不触碰数据红线的前提下验证写接口的鉴权缺失，最终通过泄露字段与其他系统的凭据关联，将危害从信息泄露升级为批量账号接管。全文重点记录每个环节的研判思路，而非单纯的复现步骤。

0x01 信息收集：从前端 JS 与配置文件中提取攻击面

目标为某高校数字校园门户，前端是 Angular 单页应用（SPA）。SPA 架构下，目录爆破的收益很低，攻击面测绘的重点应放在前端 JS 的接口提取上。

将前端打包后的 JS 全部下载，从中提取接口路径与映射关系，最终整理出 983 条 API 映射，覆盖成绩、宿舍、选课、收费、评教等全部教务业务模块。

更关键的发现来自一份静态配置文件：

该文件直接写明了内部 API 网关的地址与端口：所有业务请求经由 http://xsm.***.edu.cn:2929/jw-<子系统>i/<端点> 转发至后端微服务集群。也就是说，网关入口和接口清单都不需要猜，前端已经全部提供。

接口命名存在明显规律：读接口以 r- 或 list 开头，写接口以 w- 开头。这个规律为后续按读/写分类批量测绘提供了依据。

经验总结：未授权访问的判定，单次请求没有结论价值。响应出现”时好时坏”时，应优先怀疑负载均衡后的实例差异，连发 8~10 次观察是否存在交替规律。微服务架构下鉴权由各实例自行实现，配置不一致的情况只会越来越多，这个测试习惯直接决定这类漏洞是被发现还是被漏检。

0x03 缺陷范围测绘：对照实验与判读规则

确认缺陷模式后，下一步是确定 983 个接口中哪些可利用。逐个重试效率太低，需要先建立判读规则。这里做了两组关键实验。

1. 寻找天然对照组

在 8 个存活微服务中，jw-cssi（选课）和 jw-srsi（师资）的所有请求恒定返回 751，从不放行。这说明这两个服务的鉴权过滤器部署完整一致，可以作为”鉴权正常”的基准线，与其他服务的放行记录形成对照。

2. 利用 404 建立端点存在性判据

测试中发现一个细节：请求不存在的端点时，恒定返回 404（JSON 中带 "user":{"id":0}），从不出现交替现象。这说明 404 在鉴权检查之前触发。由此得到三条判读规则：

  • 返回 404（不交替）→ 端点不存在，直接排除；
  • 返回 751 与数据交替 → 端点存在，且在缺陷实例上可穿透鉴权；
  • 返回 400 缺参数（而非 751）→ 请求已穿透鉴权层，只差业务参数，补齐即可出数据。

按这三条规则批量测绘，结论如下：抽验约 25 个读接口，9 个确认未授权返回数据，至少 5 个确认穿透鉴权层。响应自带分页统计，各接口数据量级：

接口 总记录数 泄露内容
HmsXsjbxx/r-list 52,619 条 学生全量 PII：姓名、学号、身份证号、本人手机、家庭电话、邮箱、家庭住址、全国考生号、贷款金额、贫困生审核意见
AmsJxbXsZgcj/listXs 78,571 条 学号、姓名、学院、专业、班级、平均绩点

0x04 写接口边界验证：不改动数据前提下的鉴权穿透证明

读接口泄露已经实锤，接下来的问题是 w- 前缀的写接口（成绩提交、费用更新等）是否同样存在鉴权缺失。直接发送真实数据测试是红线——测试原则是不改动任何业务数据。

采用的验证方法是畸形参数探测：发送必然在业务逻辑执行前失败的请求（如截断的 JSON {"x":、空对象 {}）。这类请求最多走到参数解析层，不可能产生写入，但返回的错误类型可以暴露请求到达了哪一层：

写接口 响应模式 判定
AmsCjdr/w-submit（成绩导入） 751 ↔ err:1 "失败" 严格交替 缺陷实例上穿透鉴权，直达业务层
AmsJxbXscj/w-saveAll（成绩保存） 751 ↔ "无法获取当前登录用户，请重新登录！" 交替 穿透鉴权，被业务层会话校验拦下
CssCk/w-ck（选课，对照组） 恒定 751 鉴权正常

结论需要精确表述：写接口的鉴权缺失可以实锤（缺陷实例上请求穿过了 751 这道门），但部分接口的业务层存在第二道防线（会话上下文校验），实际可写性未证实。报告中按此措辞，既不夸大也不漏报。

经验总结：验证写操作类漏洞时，”畸形请求 + 错误类型分析”是在不触碰数据红线的前提下能走到的最远处。错误信息出自哪一层，就证明请求到达了哪一层。

0x05 危害升级：泄露字段与其他系统的凭据关联

到这里，漏洞性质还只是大规模信息泄露。但检查泄露字段时注意到，每条记录同时包含 qgksh（全国考生号）和 idcard（身份证号）两个字段。

而在前期的信息收集中，同站还有一个迎新系统 /welcome/login，其登录凭据恰好是考生号 + 身份证后 6 位。当时记录的该系统另外两个缺陷：

  1. 验证码为纯前端 canvas 生成，登录提交的表单中不包含验证码字段，服务端不校验验证码；
  2. 登录密码在前端使用 AES-128-ECB 加密后提交，而密钥硬编码在前端 JS 中（MD5("<校名缩写>SECRET")），可离线加密任意凭据直接构造登录请求。

三条线索组合后，攻击链成立：网关泄露的每一行记录，都是迎新系统的一组现成登录凭据。

验证过程（经授权，单账号单次）：从泄露接口取一条记录的考生号与身份证号，本地用前端同款密钥离线加密后 POST 至 /welcome/login，返回 302 跳转进入该学生后台，信息录入、选宿舍床位、缴费状态、绿色通道贫困认定等功能均可用。随即退出登录并确认会话销毁，未查看、修改任何数据。

这意味着 5.2 万名新生的迎新账号均可被直接接管，单个账号的接管成本为一次 HTTP 请求。攻击者可篡改新生信息、抢占宿舍床位、伪造贫困认定，而迎新季本身就是精准诈骗的高发期。

经验总结：信息泄露的真实危害往往不在泄露本身，而在字段的可组合性。拿到一批数据后，应评估这些字段能否充当其他系统的凭据、密保答案或社工素材。危害升级通常发生在系统与系统的接缝处。

0x06 总结与防御建议

本次测试的漏洞成因并不复杂：网关鉴权依赖各微服务实例自行实现，实例间配置不一致，约半数实例缺失鉴权过滤器，导致匿名请求有约一半概率直达业务层。但它同时具备几个值得记录的特点：单次请求即可漏检的隐蔽性、前端配置文件直接暴露内部网关、泄露字段与迎新系统凭据的完美关联。

几点测试方法论上的收获：

  1. 未授权测试的样本量就是检出率。任何”请求一次就下结论”的工具或流程，在这类实例级鉴权不一致面前都有约一半的漏检概率。重试 8~10 次应成为未授权测试的固定动作。
  2. 防御的均匀性比强度更重要。该系统并非没有鉴权——对照组服务证明过滤器本身工作正常。但鉴权逻辑下放到各实例自行实现后，任何一个实例漏配，整体防护即失效。
  3. 证据链的边界要清晰。写接口无法在不改数据的前提下证实可写，就用畸形请求证明”穿透鉴权层”并如实标注”实际可写性未证实”；账号接管只验证单账号单次，就明确写”未批量验证”。报告的可信度来自边界清晰，而不是措辞夸张。

给防守方的修复建议：

  1. 鉴权前置：排查网关全部后端实例并补齐鉴权过滤器，鉴权逻辑应前置到网关层统一强制校验，不下发到微服务自行判断；
  2. 回归测试注意重试：对全部 API 做匿名访问回归测试时，须多次重试，单次测试可能恰好命中正常实例而漏检；
  3. 限制分页与批量行为：列表接口强制分页上限（如 pageSize ≤ 100），并接入批量拉取行为告警；
  4. 收敛前端暴露面：移除或鉴权保护 assets/config/ 下的内部配置文件；
  5. 凭据体系整改：修改新生初始密码策略（弃用身份证后 6 位，改为随机密码并首登强制修改），排查迎新系统异常登录日志，评估数据泄露告知义务。

测试全程为授权范围内的只读操作（单账号登录验证一次除外，已获授权），证据样本已脱敏，原始敏感数据已全部删除。文中目标信息已做匿名化处理。
