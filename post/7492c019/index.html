被动资产收集工具的设计与迭代复盘

发表于 2026-07-27 分类于 实战复盘 本文字数： 3.5k 阅读时长 ≈ 3 分钟

0x00 前言

做企业级授权测试的信息收集，最常见的姿势是把工具列表跑一遍：subfinder、amass、FOFA、oneforall……每个工具输出一堆，最后拼出一个几千行的表格，看起来成果满满，真正到漏洞挖掘阶段能用的没几行。

我自己封装的被动资产收集工具（一个 Claude Code skill），最终形态只有三张表、十六个字段：子域名、DNS 解析、IP 归属。但这个结果是七个版本迭代出来的，不是一开始就设计成这样的。这篇记录每一版删了什么、为什么删——信息收集工具的设计里，”不做什么”比”做什么”更难决定。

0x01 起点：什么都要的代价

最初版本的思路很朴素：既然是做资产梳理，那就把能收的都收回来。公司名进去，ICP 备案查主域名，FOFA 查资产，Web 指纹跑一遍，最后交付八张表，四十多个字段。

跑起来才发现每一步都有代价：

  • 入口依赖：公司名 → ICP 备案 → 主域名这条链，备案查询接口时好时坏，解析结果还经常一对多，第一步就把流程卡住；
  • API 依赖：FOFA 要 key、要额度，key 过期整个流程报废，而且 FOFA 结果和免费源结果合并时字段互相覆盖，数据越收越脏；
  • 交付臃肿：八张表里一半字段（IP 版本、国家/地区、可信等级、备注）在后续漏洞挖掘中从来没有被用到过；
  • 流程脆弱：任何一个数据源超时或限流，整个流程死等。

研判：信息收集的交付物不是”数据库”，而是”候选线索”。它的价值取决于下游（漏洞验证）能不能直接用，而不是字段齐不齐。这个定位明确之后，后面的删减就有了统一的评判标准：这个环节是让下游更快开工，还是只是让表格看起来更全？

0x02 砍入口：只认一级域名

第一个砍的是公司名入口。v0.6.3 把”公司名 → ICP 备案 → 主域名”的默认链路整个删掉，输入只接受一级域名，公司名降级为可选备注，不驱动流程。

理由很实际：

  1. 备案查询是不稳定的外部依赖，把流程的咽喉要道架在不可控的服务上，违背”任何单一来源失败不能卡死流程”的底线；
  2. 备案结果一对多时仍需人工确认主域名，自动化省下的时间又在人工确认上还回去了；
  3. 授权测试的授权书里写的就是域名，输入即授权边界——用域名做入口，边界天然清晰，还顺带避免了”查到关联公司就顺手测了”的越权风险。

0x03 砍依赖：FOFA 不是必须品

第二个砍的是 FOFA API 接入（v0.6.1）：删除所有 FOFA 相关命令、凭据检查、额度统计，Subfinder 内部也显式排除其 FOFA 来源，防止隐式消耗额度。

这个决定当时是有犹豫的——FOFA 的数据确实全。但它带来三个结构性问题：

  • 流程可靠性和一个付费 API 的可用性强绑定，key 失效、额度耗尽都会成为单点故障；
  • 数据合并变复杂：FOFA 结果和免费源结果的字段语义不完全一致，合并时”谁覆盖谁”本身就是 bug 温床；
  • 替代方案存在：手工导出 FOFA 结果，用 import-source --stage 导入即可——把”在线依赖”变成”可选导入”，工具主流程只依赖免费、稳定、无需凭据的来源（subfinder、crt.sh、dnsx、RDAP）。

经验总结：工具设计里，”这个来源数据很好”不是接入的充分条件。要问的是：它失效时流程会怎样？它和其他来源冲突时怎么合并？能不能把它从”依赖”降级为”可选输入”？

0x04 砍字段：三张表十六个字段的诞生

这是最费力气的一部分，分了三个版本才完成：

版本 动作 理由
v0.5 8 表 → 6 表，合并一级域名与注册信息、业务系统与 Web 指纹 两张表回答的是同一个问题
v0.6.4/0.6.5 子域名表删除”可信等级””备注” 被动数据的”可信等级”是伪精确，下游从来不看
v0.6.10/0.6.11 6 表 → 3 表，删除企业主体、Web 资产、存活验证 最终收敛为：子域名 / DNS 解析 / IP 归属

最后三刀值得单独说：

删”存活验证”：早期版本会对子域名做存活判定并打标。后来发现这是语义错误——被动收集的产出本质是”当时能解析到什么”，DNS 能解析不代表业务存活，存活判定属于下一阶段（Web 资产测绘）的职责。把”数据性质”如实标注，比替下游下一个不可靠的结论更负责任。现在 DNS 表里有一列就叫”数据性质”，明说这只是解析关系。

删 Web 资产收集（stage4）：端口、标题、指纹确实有用，但那是”主动测绘”的活，和”被动收集”放在一起，既模糊了低噪声定位，又让工具职责膨胀。砍掉后整个工具保持纯被动：只用公开情报、历史归档、注册信息，不碰目标一个端口。

字段收敛到 16 个：每一列都过了一遍”下游漏洞挖掘会不会真的看这一列”。过不了的就删，没有例外。

0x05 砍出来的同时，补上两样东西

砍功能的同时，有两块反而加强了——因为它们才是工具能不能在真实环境活下去的关键。

一是防卡死工程。真实网络环境里数据源失败是常态不是意外：每个来源独立硬超时、有限重试、连续失败熔断；每完成一个来源立即落盘原始结果；失败时的降级链固定为”新鲜缓存 → 主来源 → 旧缓存 → 用户导入 → 降级跳过”；单一来源失败只标记 completed_degraded，不终止整阶段。RDAP 查询遇到 429/5xx 做指数退避并遵守 Retry-After，远端断连不导致整批中断。

二是双层证据纪律。IP 归属查询里，RDAP 原始响应完整保存在 raw/ 目录（原始层），标准字段写在 CSV 里（标准层），并且立了条硬规则：注册机构/服务商 只保留 RDAP 原始名称，CDN/云厂商标签只作为附加字段，派生标签永远不许覆盖原始证据。清洗逻辑不得丢弃原始响应。这样下游任何人质疑结论时，都能回到原始证据复核，而不是对着一个二手标签猜。

经验总结：功能收敛之后，省下来的精力应该投到可靠性和证据可复核上。功能少但每一步可信，比功能全但处处存疑更有用。

收敛后的流程固定为五步：

几个设计细节顺带一提：

  • 最小高价值路线：子域名收集不是工具越多越好。核心只有 subfinder + crt.sh 并行，基线不够时每轮最多追加一个补充源（HackerTarget / Amass）——多个工具的结果重合度很高，继续加工具主要增加的是去重成本；
  • IP 归属独立入口：--ip / --ip-file / --from-stage3 三种方式，不用重跑 DNS 就能单独查归属，因为”查一个 IP 是谁家的”在测试中段也经常需要；
  • 阶段间有状态门禁：stage5 交付前必须完成 ip-ownership，防止跳过关键步骤出半成品报告。

0x07 总结

回头看这七个版本，主线是不断区分”想要”和”需要”：大而全的资产库是想要的，下游能直接开工的候选线索才是需要的；在线 API 的便利是想要的，任何单点失效都不中断的流程才是需要的；替下游提前下结论是顺手做的，把原始证据完整保留、结论留给使用的人才是需要的。

如果你也在封装自己的信息收集工具，三条可迁移的原则：

  1. 输入即边界：入口参数直接对应授权范围，不依赖不稳定的前置解析链；
  2. 来源分级：免费稳定源做主流程，付费/不稳定源降级为可选导入，任何单一来源失败不卡死整体；
  3. 交付做减法，证据做加法：字段砍到下游真的会看的为止，原始响应一条不丢地留底。

本工具仅用于明确授权的目标，纯被动收集，不触碰目标任何端口与服务。
