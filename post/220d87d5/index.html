未授权文件上传复盘：任意文件写入的危害定界与GetShell证伪

发表于 2026-07-18 分类于 实战复盘 本文字数： 4.2k 阅读时长 ≈ 4 分钟

0x00 前言

文件上传漏洞的报告里，最常见的话术是”存在未授权上传，可上传任意文件，建议尽快修复”。但”能传”和”能利用”之间隔着三个问题：文件落没落盘？路径可不可控？Web 可不可达？任何一个答案是否，危害评级都要重定。

本文复盘某职业技术学院报名系统的一次未授权文件上传测试。这个漏洞最终定格在中危——不是因为测得不深，恰恰相反，是因为把 getshell 的三条路径全部实测排除后，证据只支持这个结论。本文重点记录这条”证伪链”：如何从大量误导性攻击面里找到真实的上传点，以及确认上传成功后，如何系统性地验证”它能坏到什么程度”。

0x01 攻击面梳理：先排除两个假目标

目标与上一篇 SQL 注入是同一系统。信息收集阶段，文件相关的攻击面看似很丰富，但逐个核实后，大部分是噪音：

假目标一：/File/* 系列接口。 前端 JS 里存在 uploadify 上传组件的完整调用（/File/UploadFile、/File/Download、/File/LoadFileInfo 等），还有一个开发者遗留的 test.jsp 演示页。但实测全部返回软 404——这是一个从其他项目拷贝来的遗留页面，页面里的 ${ctx} 占位符甚至没渲染，背后的 OPF 组件根本没部署。攻击面不存在，连带基于 /File/Download 的 IDOR 猜想一并关闭。

假目标二：/download.jsp 任意文件读取。 无参访问直接抛完整堆栈，泄露 File thefile = new File(attach.getFiledir()) 这样的代码片段，疑似路径可控。但换了四个参数名（filedir / attach.filedir / filePath / id）全部在同一个位置空指针——附件对象由数据库按 ID 装配，路径不可直接控制。同样关闭。

真实目标：ServiceAction 分发器。 登录页和 main.js 里存在一种值得警惕的 URL 形态：

例如 /ServiceAction/com.seaz.base.security.servlet.LoginAction?action=checkIsIP。URL 里直接携带后端类名，由分发器反射调用——这种设计下，所有被注册的 Action 类的攻击面都挂在同一个入口上，只要分发器本身没做鉴权，后面的每一个方法都可能未授权。

main.js 中找到了文件相关的三个类：FileUploadAction（uploadFile / getMaxUploadSize / getAttachObjnameById）、FileDownload、AttachAction（delete）。

经验总结：文件上传类目标的测绘，先分清”JS 里引用过”和”服务端真部署”。遗留测试页、拷贝来的组件引用会制造大量假攻击面，每个都要用一次请求确认死活，再决定投入方向。

0x02 分发器鉴权确认：两个无副作用的探针

先验证分发器本身有没有鉴权。这里选探针有个讲究：要找无副作用的方法调用——既不读敏感数据也不写任何东西，纯粹观察”请求是否到达了业务层”。

两个探针：

  1. 调用真实存在的方法 FileUploadAction?action=getMaxUploadSize（查询上传大小限制，纯读取配置），未登录状态下返回 -1.0——业务逻辑真实执行了，分发器没有登录校验；
  2. 调用一个不存在的类名，返回 200 空响应——分发器对任何类名都尝试分发，没有白名单。

用返回的附件 ID 把读取链路也验证了一遍（均为未登录状态）：

  • getAttachObjnameById?attachid=<GUID> → 返回 probe.txt（附件元数据未授权可读）；
  • FileDownload?attachid=<GUID>&download=1 → 文件内容原样返回；
  • download.jsp?attachid=<GUID> → 同样直接返回内容。

另外注意这个附件 ID 是 32 位 hex GUID——这顺带解释了之前附件 IDOR 枚举失败的原因：ID 空间太大，黑盒无法枚举他人附件。未授权上传 + 未授权读己知 ID 的附件，漏洞到这里已经可以定”中危”。剩下的问题是能不能升级。

0x03 GetShell 三条件逐一验证

能否 getshell，拆开是三个独立条件，逐个实测：

条件 验证方法 结果
① 文件落盘 download.jsp?attachid=<GUID> 能读回内容，且堆栈显示 new File(filedir) 成立，文件真实写在磁盘上
② Web 可达 直接访问 /upload/probe.png、/upload/<GUID>.png、/attach/<GUID>.png 等常见静态路径 不成立，全部软 404，存储目录在 Web 根之外
③ 路径可控 上传文件名构造为 ../probe_trav.txt、../../../../probe_trav2.txt，尝试穿越到 Web 根 不成立，getAttachObjnameById 返回的文件名是剥离后的 probe_trav.txt，服务端做了规范化

条件①成立但②③都不成立。还有一个细节：磁盘文件以 GUID 命名，原始文件名只存数据库字段——即使穿越成功，落地文件名也不可控。

初步结论：getshell 不成立。但路径穿越只测了最基础的两种写法，下结论前需要把常见的绕过手法补齐。

0x04 穿越绕过专项复测：六组全灭

隔了一天，对照路径穿越的技术清单做了第二轮专项测试，共六组：

组别 Payload 元数据接口返回 判定
1 反斜杠 ..\probe_bsl.txt probe_bsl.txt 反斜杠同样被剥
2a 嵌套 ....//probe_nest.txt probe_nest.txt 失败
2b 混合 ....\/probe_nest2.txt /probe_nest2.txt（残留前导/） 暴露了过滤逻辑，但不构成穿越
3a-c 编码系 ..%5c、%252e%252e%252f、..%2f 原样存活 服务端不做 URL 解码，编码串进不了落盘路径
4 RFC5987 filename*=UTF8''..%5c… probe.txt 老解析器不认 filename*，回退到普通字段
5 双 filename 同名字段传两个 取第二个，但仍被规范化 失败
6 绝对路径 C:\probe_abs.txt probe_abs.txt 被 basename 化

六组全灭。所有构造的”穿越后落点”也逐个用 GET 验证过，Web 根下均无落地文件。

到这里可以画出服务端文件名处理的完整画像：删除所有 .. 子串 + 删除反斜杠 + 按 / 取 basename，且不做 URL 解码。编码系的 payload 能活着存进数据库的元数据字段，但磁盘文件 GUID 命名、原始文件名不参与落盘路径，所以对穿越写盘的防护是完备的。

另外还有一条支线：上传不限制文件格式（HTML 也能传），但下载接口统一带 Content-Disposition: attachment 强制下载，不渲染，XSS 路径同样堵死。

最终定级：未授权上传 = 中危。可任意上传文件占用存储、污染附件库；附件元数据与下载接口未授权，但 GUID 不可枚举他人附件；getshell 与 XSS 路径均实测排除。

经验总结：危害定级是证据问题不是措辞问题。把”可 getshell”写进报告只需要一行字，但把它证伪掉需要两轮九个 payload 加一串落点验证——后者对厂商的价值反而更大：审核人员看到”穿越六组全灭、Web 根逐点验证无落地”的结论，就不需要再花时间去怀疑评级是否被压低。

0x05 总结与防御建议

本次测试的漏洞本体很简单：ServiceAction 分发器无鉴权，导致上传、元数据读取、下载三个接口全部未授权。值得记录的是测试过程本身：两个假攻击面的排除、无副作用探针的选择、getshell 三条件的逐一验证、穿越绕过的专项复测。挖洞不止要会”证实”，也要会”证伪”——把不成立的路径系统地排除掉，结论才站得住。

几点测试方法论上的收获：

  1. URL 中出现类名/方法名的分发器，优先级提到最高。这种设计把路由层和代码层直接打通，鉴权一旦缺失就是成片暴露。本次同站还存在一个 GET 型附件删除接口（AttachAction?action=delete&ids=N），疑似同样未授权，因删除属禁止操作未验证，已在报告中提示厂商自查。
  2. 写入类测试全程用无害探针并留痕。本次上传的所有文件均为自造的无害文本/1×1 像素图片，每个文件的附件 ID、文件名、用途都记录在案，报告中如实说明留存情况。
  3. 定级下调不丢人。这个漏洞从初判”高危（任意文件上传）”下调到中危，依据是三轮实测。夸大危害的报告会被审核打回，边界清晰的报告才会被快速确认。

给防守方的修复建议：

  1. ServiceAction 分发器增加统一鉴权，上传/下载/删除类 Action 必须登录且校验业务归属；同时对可分发的类建立白名单；
  2. 保持现有的存储隔离与文件名规范化（实测对穿越防护有效），建议再补服务端文件类型白名单；
  3. 附件元数据与下载接口校验当前用户对该附件的访问权限；
  4. 清理 test.jsp 等遗留测试页，关闭生产环境的详细错误回显。

测试仅上传无害探针文件（txt×3、1×1 像素 png×1 及穿越测试文本若干），未上传任何可执行文件，未读取/删除任何他人附件。文中目标信息已做匿名化处理。
