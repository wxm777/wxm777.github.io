AI渗透工作流的信息收集层重构：从工具驱动到信号驱动

发表于 2026-09-18 分类于 方法论 本文字数： 2.7k 阅读时长 ≈ 2 分钟

0x00 前言

之前写过 AI-SRC 工作流的整体架构，这篇记录信息收集层（S1）的一次重构。

重构的原因是实战中反复出现的三类问题：拿到目标先跑一轮字典爆破，几千条结果里能用上的很少；工具跑完存个文件就算结束，结果没人逐条看；以及看到登录框就直接开始测注入，验证码机制还没摸清。这三类问题的共同点是：旧版 S1 的流程是围绕”有哪些工具可以跑”组织的，而不是围绕”需要收集什么信号”组织的。

这次重构把顺序倒了过来。下面记录改动内容。

0x01 总原则：真实来源优先，字典爆破降级为补盲

新的总原则：信号驱动流程——真实来源（浏览器 Network、JS 提取、Swagger 文档）优先于字典猜测，字典爆破只在有覆盖缺口时使用，不再是每个目标的常规动作。

依据是实际观察：浏览器把功能点一遍，Network 面板里的 XHR 就是一份接口清单；SPA 的 JS chunk 里能提取出 API 注册表；有 Swagger 的站可以直接拿到接口和数据模型。这些来源的覆盖率通常比字典高，而且不产生大量请求。

字典爆破除了收益低，还有封禁风险：教育 SRC 场景下大字典扫描是触发 WAF 的常见原因（9 月 7 日实测，瑞数类动态 WAF 下大字典扫描导致 IP 被封）。降级为补盲手段后，请求量和特征都明显下降。

时间预算也做了固定：S1 约 30 分钟，SPA 站需要深逆 JS 的可到 40-60 分钟；止损条件是连续数分钟无新增高价值接口即提前结束。

0x02 八步流程

重构后的 S1 固化为八步：

三个设计细节：

探针组（第③步）替代了旧版的大字典扫描。30 到 200 发固定的高价值路径（文档端点、.git、备份文件），所有站点照跑，SPA 站不豁免。探针组里包含 WAF 预探：正常包和带特征包各发两三发做对照，尽早确认防护是否存在，为后续动作的请求强度定基调。

第⑤步的字典使用规则：目录、API、敏感路径合并去重后一次跑完；扩展名按指纹裁剪，Java 站不挂 php 后缀；动态 WAF 站点降级为小字典限速，或直接跳过并报告用户。

第⑥步的结构化接口清单表是强制产物，每行标注接口来源（Network 观察 / JS 提取 / 文档 / 爆破）。这张表是 S2 的直接输入，S1 和 S2 之间通过固定格式交接，不再用松散笔记。

0x03 强弱信号：进 S2 的判定标准

S1 何时结束、进入 S2，新标准给出了分级：

  • 强信号（≥1 个即可进入 S2）：Swagger/actuator 可解析、报错堆栈带组件版本、接口无鉴权返回真实数据、.git 可拉取、JS 硬编码密钥；
  • 弱信号（≥3 个且覆盖充分）：普通路径 200、无版本指纹、目录列表、无敏感内容的配置；
  • 两者都不足：先查 wayback 历史快照捞旧接口（学校站改版后旧接口残留比较常见），仍无则进入盲打模式。

同时保留了一条说明：”最终结合信号价值、置信度、覆盖度综合判断，不做纯计数门槛”——判据是参考基线，不是机械执行的阈值。

0x04 工具产出判读

旧版的一个问题：工具跑完结果存进 evidence/，没有逐条判读，部分命中信息没有被利用。这次加了两条强制要求：

  1. 结果强制过目：URLFinder 和 dirsearch 的输出必须按关键词过滤后逐条过一遍，命中记为信号。关键词为：api、admin、swagger、actuator、.git、backup、test、upload；
  2. 工具产出判读：每个工具跑完在 recon.md 写一行结论（产出 X 条 / 零命中 / 识别出结构特征），不允许只存证据文件不写结论。

复盘（/rem）时会把各目标的工具产出率汇总，作为后续工具链取舍的依据：某个工具在真实目标上持续零产出，就从流程里降级或移除。工具链的构成由此可以基于累计数据调整，而不是凭印象。

0x05 配套沉淀：WAF 止损决策表

知识库同步新增了一张服务 S1 的卡片：waf-decision.md，WAF 厂商止损决策表。定位是止损开关，不是绕过手册。

探针组预探发现拦截特征后，用 wafw00f 识别厂商，然后按表执行预算限制，例如：雷池语义引擎对混淆类手法不敏感，已验证的公开绕过手法对新部署无效，规则是禁止投入绕过研究；瑞数类动态 WAF 禁止大字典扫描，探测降速到 5~10 秒一发；深信服设备注入路线只给低预算。每行规则附实战来源和日期。

这张表嵌在 S1 第④步（信号分流）里：厂商识别结果直接转化为后续动作的预算约束——字典规模、探测速率、注入探针数量都按表执行。

quick-ref 索引同时加了使用限定：卡片只在流程走到对应阶段时加载，禁止拿到目标后逐项测试。

0x06 指纹确认方式升级

S1 的指纹识别规则也做了调整：旧规则要求 Shiro、Struts2 这类高价值组件必须两个指纹工具交叉确认才采信；现在改为做无害功能验证——Shiro 发 rememberMe 观察是否有 deleteMe 响应头，Fastjson 用 URLDNS 无害探测，版本号用报错堆栈或异常页佐证。

理由是工具指纹本质上是规则匹配，可能误报；功能回显是目标自身的响应，可信度更高。

0x07 总结

这次重构的改动可以归纳为四点：

  1. 信息来源分级：Network / JS / 文档作为主要来源，字典爆破降级为补盲手段；
  2. 执行顺序固定：人工走站第一，卡片按阶段加载；
  3. 产出必须判读：每个工具写一行结论，工具链取舍按累计产出率调整；
  4. 预算显性化：时间预算、止损条件、WAF 厂商预算表都写成明确规则。

这些规则基本都能对应到 9 月实战中的具体问题：有目标字典跑了半小时零产出，有站点验证码机制没摸清就进入了测试阶段。规则的主要来源是踩坑记录，这次的改动就是把这批坑固化成约束。

本工作流仅用于授权目标，所有测试遵守 SRC 平台规则与最小必要原则。
